# Code Style

This document defines the code-level standards for this codebase. It applies to every
function, file, and package — whether written by a human or generated by an AI tool.
When generating or reviewing code, treat every rule here as non-negotiable unless an
explicit comment in the code states otherwise and explains why.

---

## Write Go, Not Java or C#

Go has a distinct idiom. Code generated for this codebase must reflect that idiom.
AI tools and contributors familiar with object-oriented languages often produce Go
that is syntactically valid but idiomatically wrong — it looks like Java or C#
transliterated into Go syntax. This is not acceptable.

**No constructor functions that mirror OOP constructors:**

```go
// Bad — Java-style constructor wrapping methods on a service struct
type UserService struct {
    db     *sql.DB
    logger *log.Logger
    cache  *Cache
}

func NewUserService(db *sql.DB, logger *log.Logger, cache *Cache) *UserService {
    return &UserService{db: db, logger: logger, cache: cache}
}

func (s *UserService) ValidateUser(user User) (User, error) { ... }
func (s *UserService) SaveUser(user User) (User, error) { ... }
func (s *UserService) FetchUser(id int) (User, error) { ... }

// Good — plain functions, dependencies passed directly where needed
func validateUser(user User) (User, error) { ... }
func saveUser(db *sql.DB, user User) (User, error) { ... }
func fetchUser(db *sql.DB, id int) (User, error) { ... }
```

**No deep interface hierarchies:**
Go interfaces are satisfied implicitly and should be small — one or two methods.
An interface with ten methods is a class in disguise.

**No getters and setters:**

```go
// Bad — OOP accessor pattern
func (u *User) GetEmail() string  { return u.email }
func (u *User) SetEmail(e string) { u.email = e }

// Good — exported fields or direct struct access
type User struct {
    Email string
}
```

**No exception-style error handling:**
Go errors are values. They are returned, checked, and wrapped — not thrown, caught,
or handled in deferred recovery blocks except at true boundaries (e.g. HTTP handlers,
goroutine roots).

## Minimize Abstractions

Every abstraction has a cost: it adds a layer a reader must mentally traverse to
understand what the code is doing. Go's clarity comes from its directness. Prefer
concrete over abstract, explicit over implicit, and simple over clever.

The test for whether an abstraction earns its place:

- Does it remove genuine, recurring duplication — not just theoretical duplication?
- Does it make the code clearer to a reader, or only to the author?
- Would removing it require changing more than one package?

If the answer to any of these is no, the abstraction should not exist.

Specific guidelines:

- **Interfaces are defined by the consumer, not the producer.** Define an interface
  where you need to accept multiple implementations or write a test double. Do not
  define interfaces preemptively on every struct.
- **No wrapper types for their own sake.** A type that exists only to rename another
  type adds noise without clarity.
- **No middleware chains for single-use logic.** If something happens in exactly one
  place, write it in that place.
- **Avoid indirection through configuration structs** when plain function parameters
  are sufficient. An `Options` struct with fifteen fields is often a sign that a
  function is doing too much.

## Function Length and Single Responsibility

Functions must be short. The target is **5 to 10 lines of executable code**. This
is not a soft guideline — it is the primary mechanism by which single responsibility
is enforced in practice.

A function that grows beyond 10 lines is almost always doing more than one thing.
The correct response is not to add comments explaining the sections — it is to
extract those sections into named functions.

```go
// Bad — too long, multiple responsibilities in one function
func processOrder(order Order) (Order, error) {
    if order.ID == 0 {
        return order, fmt.Errorf("processOrder: missing id")
    }
    if order.Total < 0 {
        return order, fmt.Errorf("processOrder: invalid total")
    }
    order.Tax = order.Total * 0.08
    order.Total = order.Total + order.Tax
    order.Status = "processed"
    order.ProcessedAt = time.Now()
    return order, nil
}

// Good — each function does one thing, length is minimal
func validateOrder(order Order) (Order, error) {
    if order.ID == 0 {
        return order, fmt.Errorf("validateOrder: missing id")
    }
    if order.Total < 0 {
        return order, fmt.Errorf("validateOrder: invalid total")
    }
    return order, nil
}

func applyTax(order Order) (Order, error) {
    order.Tax = order.Total * 0.08
    order.Total += order.Tax
    return order, nil
}

func markProcessed(order Order) (Order, error) {
    order.Status = "processed"
    order.ProcessedAt = time.Now()
    return order, nil
}
```

These three functions compose naturally into a pipeline:

```go
p := pipeline.New(validateOrder, applyTax, markProcessed)
```

When a second task is needed inside a function, the choice is:

- **Direct call** — if the two functions are invariantly coupled (one must always
  follow the other), call the second directly at the end of the first.
- **Pipeline step** — if the tasks are independent and composable, add the second
  as a separate step in the pipeline.

Neither option is "add more code to the existing function."

## Cyclomatic Complexity

This codebase enforces a strict discipline around branching logic. The goal is to
keep cyclomatic complexity as close to 1 per function as possible — meaning each
function has exactly one path through it.

### The One Allowed `if`: The Guard Clause

The only permitted `if` statement inside a function is a **guard clause** at the
top. Its sole purpose is to verify that the function has what it needs to do its
work. If the precondition is not met, the function returns immediately. It does
not branch into alternative behavior — it simply refuses to proceed.

```go
// Good — a single guard clause at the top, then linear execution
func validateUser(user User) (User, error) {
    if user.Email == "" {
        return user, fmt.Errorf("validateUser: missing email")
    }
    user.Valid = true
    return user, nil
}
```

A guard clause is not a branch — it is an assertion about preconditions. The
function has one path: the precondition is met, the work is done.

### `if-else` Is Forbidden

`if-else` constructs are not permitted. An `else` block is a signal that a function
is doing two different things depending on state. That is two functions, not one.
Refactor by splitting responsibilities or using the pipeline pattern to route between
behaviors.

```go
// Bad — if-else encodes two behaviors in one function
func processUser(user User) (User, error) {
    if user.IsAdmin {
        return processAdminUser(user)
    } else {
        return processStandardUser(user)
    }
}

// Good — guard returns early, single path continues
func processUser(user User) (User, error) {
    if user.IsAdmin {
        return processAdminUser(user)
    }
    return processStandardUser(user)
}
```

Note that even the "good" example above warrants scrutiny — if `processUser` is
routing between two meaningfully different behaviors, consider whether that routing
belongs in the pipeline composition layer rather than inside a step.

### `switch` Statements

`switch` statements are **forbidden** as a general branching mechanism. They are
permitted only in strictly idiomatic Go contexts where they do not introduce
application-level branching.

**Permitted — idiomatic type switch with no business logic:**

```go
func describe(i any) string {
    switch v := i.(type) {
    case int:
        return fmt.Sprintf("integer: %d", v)
    case string:
        return fmt.Sprintf("string: %s", v)
    default:
        return "unknown"
    }
}
```

Also permitted: switches over sentinel error types in error handling infrastructure,
not in business logic.

**Forbidden — switch encoding business rules:**

```go
// Bad — switch encoding business logic branching
func applyDiscount(order Order) (Order, error) {
    switch order.CustomerType {
    case "premium":
        order.Discount = 0.20
    case "standard":
        order.Discount = 0.05
    case "new":
        order.Discount = 0.10
    }
    return order, nil
}

// Good — each rule is a named step, selected by the pipeline layer
func applyPremiumDiscount(order Order) (Order, error) {
    order.Discount = 0.20
    return order, nil
}

func applyStandardDiscount(order Order) (Order, error) {
    order.Discount = 0.05
    return order, nil
}
```

### Why This Matters

High cyclomatic complexity is the primary driver of:

- **Hard-to-test code.** Every branch requires its own test case. A function with
  five branches needs at minimum five tests; a function with one path needs one.
- **Hard-to-reason-about code.** A reader must mentally simulate multiple execution
  paths simultaneously. Linear functions are read top to bottom.
- **Fragile code.** Branches interact — adding a new branch can affect the behavior
  of existing ones in non-obvious ways.

Keeping each function to a single path through a guard-plus-linear-execution structure
means the entire complexity of the system lives in its composition, not inside its
individual pieces.

## Prefer the Standard Library

The Go standard library is comprehensive, well-documented, stable, and carries no
dependency cost. It is the default choice for every problem it can solve. External
libraries are a last resort, not a first reach.

### The Rule

Before adding an external dependency, verify that the standard library cannot
satisfy the requirement. If it can — even partially — use it.

```go
// Bad — external library for something the standard library handles
import "github.com/pkg/errors"

return errors.Wrap(err, "validateUser")

// Good — standard library
return fmt.Errorf("validateUser: %w", err)
```

```go
// Bad — external router when net/http ServeMux is sufficient
import "github.com/gorilla/mux"

// Good — standard library router (Go 1.22+ supports method and path parameters)
mux := http.NewServeMux()
mux.HandleFunc("GET /users/{id}", handleGetUser)
```

### When an External Dependency Is Justified

An external library earns its place only when:

- The standard library genuinely cannot satisfy the requirement — not merely that
  the external library is more convenient or familiar.
- The library is widely adopted, actively maintained, and has a stable API.
- The benefit it provides is proportionate to the cost of the dependency — a library
  that adds one function is never justified; one that provides a complete, well-tested
  implementation of a complex protocol may be.
- The decision is documented with a comment or ADR explaining why the standard
  library was insufficient.

### Dependency Hygiene

When an external dependency is accepted:

- Pin to a specific version in `go.mod` — never use a floating or pseudo-version
  in production code.
- Prefer libraries with minimal transitive dependencies. A library that pulls in
  twenty sub-dependencies multiplies the surface area for breakage, licensing
  issues, and security vulnerabilities.
- Treat each dependency as a long-term maintenance commitment. Adding is easy;
  removing is hard.

### What This Looks Like in Practice

| Need | Standard library solution |
|---|---|
| HTTP server and routing | `net/http` (Go 1.22+ for method and path parameters) |
| JSON encoding/decoding | `encoding/json` |
| Structured logging | `log/slog` (Go 1.21+) |
| Error wrapping and inspection | `fmt.Errorf` + `errors.Is` / `errors.As` |
| Context propagation | `context` |
| Testing | `testing` + `testing/quick` for property tests |
| Time and duration | `time` |
| String manipulation | `strings`, `strconv`, `unicode` |
| Cryptography | `crypto/*`, `crypto/hpke` (Go 1.26+ for hybrid public key encryption) |
| Database access | `database/sql` |
| Pointer field initialization | `new(expr)` (Go 1.26+ — no helper function needed) |

If a need appears in this table, the standard library solution is the answer. No
discussion required.

### Go 1.26 Modernizers

Go 1.26 ships a revamped `go fix` command with a suite of built-in modernizers —
static analysis tools that detect outdated idioms and apply safe, push-button
rewrites to bring code up to current standard library APIs and language features.
Run `go fix ./...` as part of regular maintenance to keep the codebase current.
This is especially relevant when AI tools generate code: modernizers catch cases
where generated code uses older patterns that have cleaner standard library
replacements in current Go.

## Code Comments

Comments in this codebase follow the Go community standard as defined by the
official Go documentation guidelines and enforced by `go doc` and `golint`. Comments
are not optional on exported identifiers — they are part of the public contract of
the code.

### The Golden Rule

A comment explains *why* something exists or *what* it does at a level the code
itself cannot express. Comments that restate the code in different words add noise
without value and should not exist.

```go
// Bad — restates the code
// increment i by 1
i++

// Bad — states the obvious
// validateUser validates a user
func validateUser(user User) (User, error) { ... }

// Good — adds meaning the code cannot express on its own
// validateUser checks that the user has a non-empty email address before
// the record is written to the database. It marks the user as valid on success.
func validateUser(user User) (User, error) { ... }
```

### Exported Identifiers Must Be Commented

Every exported identifier — functions, types, structs, interfaces, constants, and
variables — must have a doc comment. This is not a style preference; it is a
community standard enforced by `golint` and expected by `go doc`.

A missing comment on an exported identifier is a bug in the same way a missing
test is a bug.

**Exported functions:**

```go
// LoggerFrom retrieves the slog.Logger stored in ctx.
// If no logger is present, it returns the default slog logger as a safe fallback.
func LoggerFrom(ctx context.Context) *slog.Logger { ... }
```

**Exported types and structs:**

```go
// Pipeline executes an ordered sequence of Steps, passing the output of each
// as the input to the next. It short-circuits and returns the first error encountered.
type Pipeline[T any] struct {
    steps []Step[T]
}
```

**Exported interfaces:**

```go
// Processor defines a single-method interface for types that can transform
// a value of type T, returning the result or an error.
type Processor[T any] interface {
    Process(T) (T, error)
}
```

**Exported constants and variables:**

```go
// DefaultTimeout is the maximum duration a pipeline step is permitted to run
// before the context is cancelled.
const DefaultTimeout = 30 * time.Second
```

### Comment Format

Go doc comments follow a precise format. Deviation from this format breaks `go doc`
output and is considered non-idiomatic.

- **Start with the name of the identifier.** The first word of a doc comment must
  be the name of the thing being documented. This is how `go doc` identifies and
  formats documentation.

  ```go
  // Run executes each Step in order...   ← correct: starts with "Run"
  // Executes each Step in order...       ← incorrect: does not start with name
  ```

- **Write in plain English.** Comments are prose, not code. Use complete sentences
  with correct punctuation. Avoid jargon, abbreviations, and technical shorthand
  that a new contributor would not immediately understand.

- **First sentence is the summary.** The first sentence of a doc comment appears
  as the one-line summary in `go doc` output and package indexes. It should stand
  alone as a complete, useful description of the identifier.

- **Use present tense.** Describe what the function does, not what it did or will do.
  ```go
  // SaveUser writes the user record to the database.   ← correct
  // SaveUser will write the user record to the database. ← incorrect
  ```

- **Package-level comments** describe the purpose of the package as a whole and
  appear directly above the `package` declaration:
  ```go
  // Package pipeline provides a generic, ordered step execution type for
  // transforming values through a sequence of operations with automatic
  // error short-circuiting.
  package pipeline
  ```

### Unexported Identifiers

Unexported functions, types, and variables do not require doc comments but should
have one when:

- The logic is non-obvious and a future reader would benefit from explanation.
- The function encodes a business rule or invariant that is not apparent from
  the code alone.
- The function is long enough that its purpose warrants stating upfront (though
  by the function length rules, this situation should be rare).

Use a plain inline comment for unexported identifiers — no special format is required:

```go
// applyTax computes and adds sales tax to the order total.
// Tax is stored separately on the order for reporting purposes.
func applyTax(order Order) (Order, error) { ... }
```

### What Not to Do

- **Do not comment out code.** Dead code is removed, not commented. Version control
  preserves history — commented-out code is noise that implies the code might
  return, creating confusion about intent.
- **Do not use inline comments to explain branching.** If a branch requires a
  comment to explain what it is doing, the branch should be extracted into a named
  function whose name provides the explanation.
- **Do not write TODO comments without a linked issue.** A `TODO` with no context
  or tracking reference is permanent. If something needs to be done, either do it
  or open an issue and reference it: `// TODO(#42): handle empty email case`.

## Quick Reference

| Concern | Rule |
|---|---|
| Go idiom | Write Go, not Java/C# — no OOP constructors, getters/setters, or deep interfaces |
| Standard library | Default to stdlib — external dependencies require documented justification |
| Abstractions | Minimize — every abstraction must earn its place with concrete justification |
| Function length | 5–10 lines target — if longer, extract into a new function |
| Second responsibility | Direct call (invariant) or new pipeline step — never expand the existing function |
| `if` (guard clause at top) | Permitted — one per function, precondition check only |
| `if` (mid-function) | Forbidden — refactor into a separate step |
| `if-else` | Forbidden — split into separate functions |
| `switch` (type switch, no business logic) | Permitted |
| `switch` (business logic / state branching) | Forbidden — use pipeline composition |
| Cyclomatic complexity | Target of 1 per function — one path, linear execution |
| Exported identifiers | Doc comment required — starts with the identifier name, plain English, present tense |
| Unexported identifiers | Comment when logic is non-obvious or encodes a business rule |
| Commented-out code | Forbidden — delete it, version control preserves history |
| TODO comments | Must include a linked issue reference — `// TODO(#42): description` |
